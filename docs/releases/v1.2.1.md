# Configra v1.2.1

This patch fixes cross-environment Config copying and operator-facing credential
workflows, and builds all shipped binaries with Go 1.26.9. It remains compatible
with configra-go v1.2.0. The MySQL schema stays at **4**.

本次修复同名 Config 首次跨环境复制、含糊的错误提示、凭据有效期与标识复制体验，
并更新 Go 安全补丁。SDK 保持 v1.2.0；从 Configra v1.2.0 升级不需要数据库结构迁移。

## Changes / 变更

- **Copy to environment** creates v1 of the same Config in an empty target
  Environment. Existing/concurrently created targets are rejected. **Clone**
  still requires a globally unused Config key and now explains that restriction.
  The UI pins the saved source version, uses searchable active Environments,
  shows Vault warnings and links to the copied result. [Copy guide](../config-copy.md)
- Config errors identify the failing field and safe reason. Failed-operation
  replay retains that reason. Transfer/Clone/Restore retries preserve Operation
  IDs; conflict handling offers an explicit fresh preview. Restore waits for the
  complete new snapshot before enabling another copy. Completed transfer retries
  survive source/target archival, including legacy successful operation digests.
- Format-only changes create a new Config version even when JSON/YAML canonical
  text is identical. Parser error text cannot leak Config content into errors.
- Token creation explains invalid expiry/scopes and the effective lifetime policy.
  Date controls show elapsed days and overrun, with bounded presets. Expired Tokens
  display as expired. Certificate forms show the expiry capped by their issuer.
- CA IDs, complete SHA-256 fingerprints, client issuer IDs and Token identifiers
  are visible and copyable, with success/failure feedback. Write errors retain
  Request IDs and expose the Operation ID for Audit search. Mobile selectors and
  Administration navigation remain usable.
- Machine authentication reuses two fixed SQL prepared statements to reduce
  database round trips. Authorization results remain uncached: grants, token
  expiry/revocation and certificate/issuer status are read on every request.
- CI, release packaging, Docker builders and runtime-license evidence move from
  Go 1.26.7 to **1.26.9**, including the October security fixes. See the
  [official release history](https://go.dev/doc/devel/release#go1.26.9).
- Kubernetes updates `golang.org/x/net` to v0.60.0 and its required companion
  modules to remove the five reachable HTTP/2 findings. Kubernetes source builds
  now require Go **1.26.9**; downloaded binaries need no installed Go toolchain.
  The core/CLI and SDK language-compatibility floor remains Go 1.25.13.

## Upgrade from v1.2.0 / 从 v1.2.0 升级

1. Download the matching platform bundle and verify `SHA256SUMS`. Preserve the
   current binary/image and configuration, and take the usual verified backup.
   The bundle contains `configra`, `configractl` and `configra-kubernetes`.
2. Drain automated writes and restart the Management, API and workers with the
   matching v1.2.1 build. For source/image installations, build from tag `v1.2.1`
   using its pinned Dockerfile or release build script. Bootstrap, ports, Master
   Key and service-account grants are unchanged; do not reinitialize the database.
3. No `migrate` step or new MySQL/ClickHouse DDL is required from v1.2.0. The
   database remains schema **4**; failure detail uses the existing Operation JSON
   column. Run `configra doctor --config <doctor-config> --verify-vault` with the
   existing dedicated doctor credentials, then check readiness and a real mTLS read.
4. Reload the Management page to load the matching UI. Test a first Config copy
   into an empty nonproduction target, confirm existing targets are protected,
   and check Audit and target Vault bindings. Save unsaved edits before copying.
5. Upgrade the CLI/Kubernetes executable from the bundle if used. The SDK remains
   configra-go v1.2.0; no Go API or CRD change is required. Resume writers after
   verifying reads and audit delivery.

从更早版本升级，仍需遵循 [v1.1.0 的 schema 2→3 / MFA 说明](v1.1.0.md) 和
[v1.2.0 的 schema 3→4 迁移流程](v1.2.0.md)。不能因为本次是补丁版本而跳过历史迁移。

## Rollback / 回退

Schema 4 and existing Config/Vault data formats are unchanged. A binary rollback
requires stopping new writers and verifying the target version against a restored
copy first. Older versions do not understand the new first-copy request or the
new complete transfer digests; investigate uncertain operations in Audit/history
before resubmitting them. Do not delete Operation rows to force a retry. Rolling
back to v1.2.0 also reintroduces the corrected UX/transfer bugs and its older Go
runtime; prefer a forward patch. A data rollback requires restoring the matching
backup and reapplying subsequent revocations as described in v1.2.0's recovery guide.

## Verification
