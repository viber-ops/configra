# Configra v1.2.0 / configra-go v1.2.0

This release adds the Cobra-based [`configractl`](../cli.md), immutable
[Config+File release sets](../release-sets.md), pre-install SDK validation,
two-phase deployment credential rotation, shared [human session control](../session-control.md),
private [operational metrics](../../deploy/monitoring/README.md), write admission,
bounded [archived Outbox cleanup](../data-retention.md), and production deployment
and backup references. CLI flags and commands use Cobra/pflag; credentials and
content are supplied through files/stdin, not raw secret command-line flags.

本版补齐 Go CLI、整套发布与回滚、SDK 生效前校验、凭据两阶段轮换、共享会话撤销、
监控告警、读写资源保护及安全归档清理。写令牌仍只能由 OIDC 登录并完成 MFA 的管理
员签发；CLI 不获得用户/角色、环境生命周期或 Master Key 权限。

## Upgrade from v1.1.0 / 从 v1.1.0 升级

1. Schedule a maintenance window. Suspend automated writers, drain and stop all
   Management/API replicas and workers. Preserve the exact old images/bootstrap
   and Master Key; take a verified MySQL backup and an independent ClickHouse
   recovery point. A versioned rollback needs that complete pre-upgrade state.
2. Provision the temporary [migration role](../../deploy/mysql/README.md); apply
   the table-level service roles after step 4 creates the new tables. Running API
   and Management no longer need DDL. The API adds SELECT/INSERT/UPDATE on the
   release tables; Management adds shared session policy access. Preserve the
   documented locking-read grants. Keep a temporary migration account available
   only for this window. Bootstrap remains `version: 1`; no key format changes.
3. Run the **v1.2.0** binary with the original Master Key:

   ```sh
   configra migrate --config /run/configra/migration.yaml \
     --confirm-database configra --timeout 10m
   configra doctor --config /run/configra/doctor.yaml --verify-vault --timeout 10m
   ```

   The storage-only files reference their separate DSN environment variables and
   matching Master Key path. `migrate` confirms the configured database name,
   obtains the existing migration lock and verifies the Sentinel before upgrade.
   The returned `schema_version` must be **4**. Initialization is also supported
   for a deliberately selected empty database; do not use it as a recovery repair.
4. Schema **3 → 4** adds `management_session_policies`, `config_release_sets`,
   `config_release_states`, and the Outbox `(status,completed_at,id)` retention
   index. Existing identities, Operations, Config/Vault histories and ciphertext
   are retained. No new encrypted value table or ClickHouse column is required.
   Adding the index may take time on large Outboxes; measure on a restored copy.
5. Start matching Management/API binaries with service accounts, verify readiness,
   an actual mTLS content read, write/audit and session control. Old binaries reject
   schema 4, so mixed-version startup and rolling downgrade are unsupported.
   Revoke/discard the temporary migration credentials after verification.
6. Upgrade SDK, CLI and Kubernetes consumers. Existing current-value reads keep
   their semantics; complete release consistency is **opt-in** through release
   APIs, `UseRelease`, or the Kubernetes `type: release` source. Upgrade the CRD
   before using that source. Existing Token/mTLS scopes and expiry still apply.
7. Configure private metric scraping/independent alerts, rotation lead times,
   backup scheduling and recovery-point freshness. Review the per-process write
   limits before high-rate automation. Outbox pruning stays explicit and defaults
   to preview; there is no automatic history or Operation deletion.

升级时先停写和备份，用临时数据库迁移身份与原 Master Key 执行 `migrate`，确认
schema 为 4 并通过 doctor，再启用常驻受限账号。新版能够直接执行更早的增量迁移；
从 v1.0.1 升级时还应先阅读 [2→3 的权限和 MFA 变化](v1.1.0.md)。不要将旧程序
连接到已升级数据库，也不要通过手工删版本记录来降级。

## Rollback and recovery / 回退与恢复

Stop every new-version replica and writer, restore the complete pre-upgrade
database/key/bootstrap combination in isolation, and start the matching old
binary. New-version writes after that recovery point are outside the rollback
backup; agree on the data-loss window before proceeding. Do not remove scope,
release or policy tables in place to make an old binary start.

恢复较旧备份也会恢复当时的授权状态。开放流量前，核对并重新应用备份点之后的
Token/CA 吊销及用户 block/invalidate；无法核实的身份先失效。doctor 证明加密状态
可验证，不证明撤权状态或应用配置已经符合当前要求。

## Verification scope

The suite covers real MySQL 8.0.22/NATS/ClickHouse SDK/CLI operations, full
17-File release activation/rollback, two-phase credential rotation, session
revocation across shared stores, negative permissions and metadata-only audit.
Restricted MySQL roles are tested using the shipped SQL, including 3→4 migration
and the absence of DDL/content-delete privileges on service accounts. Mixed
read/File/certificate bursts exercise 429/Retry-After while preserving reads.

Final candidate evidence and release gates are tracked in
[production readiness](../production-readiness.md). References and local fixture
tests do not claim deployment to the user's actual database, S3 bucket, identity
provider, fault domains or monitoring system.
