# Configra v1.1.0 / configra-go v1.1.0

[Token model and API](../scoped-write-tokens.md) · [令牌与 API](../scoped-write-tokens.zh-CN.md)

Automation can write explicitly authorized Config/Vault resources and issue
read-only deployment credentials using a scoped machine identity. Write-token
issuance remains on Management and requires Administrator login plus verified
OIDC MFA. Existing read clients and the Kubernetes module remain compatible.

自动化可以用有范围的机器身份写入 Config/Vault，并签发只读部署凭据。写令牌仍只能
由管理端已登录且具有 OIDC MFA 证明的管理员签发。旧只读 SDK 与 Kubernetes 接入兼容。

## Upgrade from Configra v1.0.1 / 从 v1.0.1 升级

1. Schedule a maintenance window. Stop all Management/API replicas and workers.
   Back up MySQL and ClickHouse using the existing [backup procedure](../../deploy/backup/README.md),
   and preserve the current Master Key, bootstrap files and old binaries.
   安排维护窗口，停止全部 Management/API 副本与 worker，按既有流程备份 MySQL、
   ClickHouse，并保留原 Master Key、冷启动配置和旧程序。
2. Replace the service binary/image with **v1.1.0**. Bootstrap YAML stays `version: 1`;
   no new dependency or key format is required. API database credentials must now
   allow runtime Config/Vault/Token/certificate/Operation/Outbox mutations; only
   Management needs DDL privileges. Optionally set `write_tokens.max_ttl_days` in
   Management (1–90, default 90).
   更新为 v1.1.0；YAML 仍为 `version: 1`，无新依赖或密钥格式变化。为 API 数据库
   账号提供运行时 Config/Vault/Token/证书/Operation/Outbox 写权限；仅 Management
   需要 DDL 权限。可配置更短的写令牌期限。
3. Start one v1.1.0 Management replica with the **original** Master Key. Its
   migration lock and Sentinel check protect the automatic **MySQL schema 2 → 3**
   migration. It adds Token kind (existing rows default to `read-only`), JSON
   Config/Namespace allowlists, issuer linkage and deployment certificate binding,
   indexes/foreign key and mandatory writer expiry/mTLS constraints. Config/Vault
   histories, digests, grants, certificate/CA data and encrypted values are retained.
   先用原 Master Key 启动一个新版 Management；锁与 Sentinel 验证保护自动
   schema 2 → 3 迁移。新增令牌类型、JSON 白名单、issuer 关系和证书绑定，以及
   索引/外键与写令牌强制过期/mTLS 约束。已有数据、权限及加密内容保留。
4. Management also applies idempotent ClickHouse `ADD COLUMN IF NOT EXISTS`
   migrations for Audit `source_ip` and `field_key`, defaulting historical rows to
   empty strings. Existing audit receipts remain decodable and retryable.
   Management 同时幂等添加 ClickHouse 审计列 `source_ip`、`field_key`，旧记录
   默认空字符串，旧审计 Outbox 仍可解码、重试。
5. Verify Management readiness and `SELECT MAX(version) FROM schema_migrations`
   returns **3**. Start the other v1.1.0 replicas and API, then verify readiness,
   existing read-only credentials and a fresh scoped credential. API verifies the
   schema and never migrates it; old service binaries reject schema 3, so mixed
   versions/rolling downgrade are unsupported.
   确认 Management 就绪、schema 最新版本为 3，再启动其他新版副本与 API，验证
   原只读凭据及新写令牌。API 不迁移 schema；旧程序拒绝 schema 3，不能混跑或滚动降级。
6. Configure signed MFA `amr` evidence at the IdP and log administrators in again
   before writer issuance. Upgrade automation with
   `go get github.com/viber-ops/configra-go@v1.1.0`; existing SDK read calls need no
   changes. New write APIs require server v1.1.0. Replace deployed identities before
   revoking their scoped issuer because revocation cascades.
   配置 IdP 的签名 MFA `amr` 声明并重新登录管理员。自动化升级 SDK 至 v1.1.0；
   旧读取调用无需改动，新写接口需要服务端 v1.1.0。吊销 writer 前替换部署身份。

Rollback means stopping all replicas, restoring the complete pre-upgrade backup
and original Master Key, then starting v1.0.1. Do not strip scope columns or
downgrade Token kinds in place: doing so could widen authorization.

回退时停止全部副本，恢复完整升级前备份与原 Master Key，再运行 v1.0.1。不要原地
删除 scope 列或降级令牌类型，这可能扩大权限。

## Verification / 验证

`make test-integration` includes the v2 migration, MFA/authorization regressions,
and the SDK operator E2E against MySQL 8.0.22, NATS and ClickHouse over HTTPS/mTLS.
The operator uploads server YAML and 17 secret File fields; checks also cover
outside-scope 403, expiry/revocation, read-only delegation, retained history,
audit identity/IP/field metadata and secret redaction. CI additionally runs race
tests, vet, module integrity/vulnerability checks, UI regressions and service
images. Production capacity and Kubernetes acceptance are separate release gates
as described in [production readiness](../production-readiness.md).

集成检查包含真实依赖的迁移、MFA、SDK operator（YAML + 17 个文件）、范围外 403、
过期/吊销、只读委派、历史、审计与脱敏。CI 另有 race/vet/模块及漏洞、UI 和服务镜像
检查；生产容量与 Kubernetes 验收仍按既有发布门槛独立执行。
