# Configra v1.4.0

This release resolves six issues reported from daily use. Configs can be
created in several Environments at once, and the editor inserts Vault
references for you. Whole Vault Items can be imported from YAML, Vault Fields
keep the order they were added in, and new Vault Items open after creation.
Switching Configs keeps the Environment. It also adds a searchable Environment
picker and moves to Go 1.26.11 for a reachable `net/http` crash fix. It remains
compatible with configra-go v1.2.0. The MySQL schema stays at **4**, and no
configuration change is needed.

本版解决了日常使用中反馈的六个问题（#50–#55）：
- 新建 Config 可一次写入多个环境；
- 编辑器可直接插入 Vault 引用；
- Vault Item 可从 YAML 一次导入；
- Vault 字段保持添加顺序；
- 新建 Vault Item 后直接进入详情；
- 切换 Config 时保留当前环境。

同时提供可搜索的环境选择器，并升级到 Go 1.26.11 修复可被触发的 `net/http` 崩溃问题。SDK 保持 v1.2.0；从 v1.3.1 升级不需要数据库结构迁移，也不需要修改配置。

## Changes / 变更

**Configs**
- **New config in several Environments**
  ([#50](https://github.com/viber-ops/configra/issues/50), [#60](https://github.com/viber-ops/configra/pull/60)).
  Pick several Environments, and each gets its own first version of the same
  content. Each Environment is validated before anything is written. An
  Environment that already has the Config is shown as a conflict and left
  untouched. Every target reports its own result, and **Retry failed
  Environments** repeats only the failures with their original operation IDs.
  The copies are independent: later edits are not synchronised.
- **Insert Vault reference**
  ([#51](https://github.com/viber-ops/configra/issues/51), [#59](https://github.com/viber-ops/configra/pull/59)).
  While editing the current version, Admins can search Vault Items and choose a
  Text or Secret Field. `{vault.<namespace>.<item>.<field>}` is then inserted
  as one undoable edit. Placement follows the YAML/JSON syntax tree:
  - it goes inside empty quotes, over a selected whole value, or as a new
    quoted value after `key:`, `-`, `[` or `,`;
  - it is never spliced into a key, a comment, a nested block or the middle of
    a value.

  The picker reads Item metadata only. It warns when no Variant covers the
  current Environment and refuses archived Items and File Fields.
- **Switching Configs keeps the Environment**
  ([#52](https://github.com/viber-ops/configra/issues/52), [#56](https://github.com/viber-ops/configra/pull/56)).
  If the new Config has a version there, it opens in the same Environment, and
  Back still works. Otherwise you choose one, as before.
- **Searchable Environment picker**
  ([#43](https://github.com/viber-ops/configra/pull/43), from TechLinF's [#39](https://github.com/viber-ops/configra/pull/39)).
  The select, search box and pager become one combobox. You can type to search
  on the server, use the arrow keys and Enter, and use PageUp/PageDown past the
  first fifty Environments. The closed control shows the display name and key.

**Vault**
- **Import from YAML**
  ([#55](https://github.com/viber-ops/configra/issues/55), [#61](https://github.com/viber-ops/configra/pull/61)).
  One file creates one new Item with one Variant shared by the Environments it
  lists. You can paste it, choose a `.yml`/`.yaml` file, or start from the
  template.
  - **Check file** is a strict, read-only check
    (`POST /v1/vault-items/import-preview`, Admin only). Problems are listed by
    path and line and never include values.
  - A clean file fills the usual create form for review, in file order and with
    Secret values hidden. **Create Vault item** then writes it in one request.
  - Unknown or archived Environments, and an existing Item with the same key
    (archived or not), are rejected. Import never overwrites.
- **Fields keep the order they were added**
  ([#54](https://github.com/viber-ops/configra/issues/54), [#57](https://github.com/viber-ops/configra/pull/57)).
  Renaming a Field keeps its place, new Fields go last, and history keeps each
  revision's order. For Items saved before this release, Fields created in the
  same save keep their key order (the original order was not recorded), and
  Fields added in later saves follow in the order they were added.
- **A new Item opens after creation**
  ([#53](https://github.com/viber-ops/configra/issues/53), [#56](https://github.com/viber-ops/configra/pull/56)).
  A create retried after a lost response replays with the same operation ID
  instead of failing.
- **Vault search** also matches the Field keys of each Item's current revision
  ([#59](https://github.com/viber-ops/configra/pull/59)). Values are never
  searched.

**Security** ([#58](https://github.com/viber-ops/configra/pull/58))
- Builds and images use Go **1.26.11** for GO-2026-6859. When a request body
  exceeded `MaxBytesReader`'s limit, an HTTP/1 handler setting a header at the
  same time could crash the process.
- brotli 1.2.7 (GO-2026-6888, excessive memory on crafted streams) and
  klauspost/compress 1.20.2 (GO-2026-6865, panic on two-block frames).
- `govulncheck` reports no vulnerabilities in either module. See the
  [verification record](../verification/2026-11-10.md).

**API notes for integrations / 接口说明**
- In Vault Item read responses, `snapshot.fields` now follows the order the
  Fields were added, not key order. Field identity, values and the structure
  hash are unchanged. Clients that compared Field lists by position should
  compare by key.
- `GET /v1/vault-items?q=` also matches current Field keys.
- New Admin-only read: `POST /v1/vault-items/import-preview`
  ([UI and API notes](../ui.md#vault-import-from-yaml--从-yaml-导入-vault-item)).

## Upgrade from v1.3.1 / 从 v1.3.1 升级

1. Preserve the current binary/image and configuration and take the usual
   verified backup.
2. Restart Management, API and workers with the matching v1.4.0 build, and
   redeploy the v1.4.0 Kubernetes integration image if you use it. Cold-start
   configuration, ports, Master Key and service-account grants are unchanged.
3. No `migrate` step or new MySQL/ClickHouse DDL is required. The database
   remains schema **4**.
4. Reload the Management page.

从 v1.2.x 升级请先阅读 [v1.3.0](v1.3.0.md)；从更早版本升级，仍需依次完成 [v1.1.0](v1.1.0.md) 与 [v1.2.0](v1.2.0.md) 的迁移步骤。

## Rollback / 回退

v1.4.0 adds no tables or columns and changes no stored data. Items and
revisions written by v1.4.0 remain readable by v1.3.1. Rolling back to v1.3.1
binaries:
- shows Vault Fields in key order again;
- removes the import, multi-Environment create and reference picker;
- needs no database action.

v1.4.0 没有新增表或字段，也不改变已存储的数据；回退到 v1.3.1 后字段恢复按键排序显示，不需要任何数据库操作。
