# Configra v1.5.0

This release makes it quick to give an existing Vault Item a Variant for another
Environment. A new Variant can start as a copy of another Variant's values, or
come from a YAML file. The Item keeps its Namespace, key and Vault references. It
also includes routine dependency updates. It remains compatible with configra-go
v1.2.0. The MySQL schema stays at **4**, and no configuration change is needed.

本版解决 [#66](https://github.com/viber-ops/configra/issues/66) 与 [#67](https://github.com/viber-ops/configra/issues/67)：为已有 Vault Item 新增环境 Variant 时，可以复制其他 Variant 的值，也可以从 YAML 文件导入，Item 的 Namespace、键和 Vault 引用保持不变。
同时包含常规依赖更新。SDK 保持 v1.2.0；从 v1.4.1 升级不需要数据库结构迁移，也不需要修改配置。

## Changes / 变更

**Copy a Variant's values**
([#66](https://github.com/viber-ops/configra/issues/66), [#68](https://github.com/viber-ops/configra/pull/68))
- In the Item editor, **Values for a new Variant** offers **Blank** (the default)
  or a copy of any Variant, listed with the Environments that share its values.
- The new Variant has its own ID, a one-time copy of every Text, Secret and File
  value, and no Environments. Secrets stay hidden. Later changes to either Variant
  do not affect the other.
- Nothing is written until **Save item**, and Cancel leaves the Item as it was.

**Import a Variant into an existing Item**
([#67](https://github.com/viber-ops/configra/issues/67), [#68](https://github.com/viber-ops/configra/pull/68))
- When the file names an Item that already exists, **Import YAML** offers **Add as
  a new Variant**. It never switches by itself, and it never overwrites a Variant.
- The file format is unchanged. The file must give a value for every Field of the
  Item with the same type, and nothing else. A value is never taken from another
  Variant; write `""` for an empty one.
- The Item's display name, Field names and Field order stay as stored, whatever
  the file says.
- These stop the import with a problem naming the Field or Environment:
  - a missing, unknown or differently typed Field;
  - an Environment that a Variant of the Item already serves;
  - an archived Item, or an Item with a File Field.
- A clean check shows a summary (Item, revision, Environments, Field count) and
  writes nothing. **Review in the editor** opens the Item editor with the new
  Variant appended and selected, and **Save item** writes it. The Item then opens
  on the new Variant.
- A concurrent change is a `revision_conflict` that keeps the draft. If the Item
  changed after the check so that the file no longer fits, nothing is loaded.
- The import message for an existing Item changed: it no longer says that import
  only creates new Items.

**Environment bindings in the editor** ([#68](https://github.com/viber-ops/configra/pull/68))
- An Environment held by another Variant is labelled with that Variant.
- Ticking it still moves it. The editor now states which Variant lost it and
  offers **Undo**.
- On phones, the Variant list wraps instead of scrolling sideways.
- See the [UI notes](https://github.com/viber-ops/configra/blob/v1.5.0/docs/ui.md#add-a-variant-to-an-existing-item--向已有-item-新增-variant).

**Dependencies**
- go-jose 4.1.9 and `golang.org/x/oauth2` 0.38.0 ([#64](https://github.com/viber-ops/configra/pull/64)).
- UI build tools: Playwright 1.65.0 and Vite 8.3.6 ([#65](https://github.com/viber-ops/configra/pull/65)).
- These are routine updates; no security advisory applied to v1.4.1.

**API notes for integrations / 接口说明**
- `POST /v1/vault-items/import-preview` accepts an optional
  `"target": "existing_item"`. Without it the behaviour is unchanged, including
  `item_exists` for an existing Item.
- With it, a clean file returns the draft with the Item's own Fields plus
  `"existing": {"revision": N, "variants": N}`. New problem codes:
  `item_not_found`, `item_has_file_field`, `field_missing`, `field_unknown`,
  `field_type_mismatch` and `environment_bound`. `field_missing` and
  `item_has_file_field` name the Field in `key`.
- The preview is still Admin-only, reads the Item without values, and writes and
  audits nothing.
- Saving is the existing `PUT /v1/vault-items/{namespace}/{item}`. As since
  v1.4.1, that save also removes edge whitespace from older single-line Text
  values in every Variant; the editor lists them before saving.

## Upgrade from v1.4.1 / 从 v1.4.1 升级

1. Preserve the current binary/image and configuration and take the usual
   verified backup.
2. Restart Management, API and workers with the matching v1.5.0 build, and
   redeploy the v1.5.0 Kubernetes integration image if you use it. Cold-start
   configuration, ports, Master Key and service-account grants are unchanged.
3. No `migrate` step or new MySQL/ClickHouse DDL is required. The database
   remains schema **4**.
4. Reload the Management page.

从 v1.4.0 升级请先阅读 [v1.4.1](v1.4.1.md)；从 v1.3.x 升级还需阅读 [v1.4.0](v1.4.0.md)；从 v1.2.x 升级还需阅读 [v1.3.0](v1.3.0.md)；从更早版本升级，仍需依次完成 [v1.1.0](v1.1.0.md) 与 [v1.2.0](v1.2.0.md) 的迁移步骤。

## Rollback / 回退

v1.5.0 adds no tables or columns. Variants it stored are ordinary Vault revisions
that v1.4.1 reads unchanged. Rolling back to v1.4.1 binaries removes the copy and
add-Variant import from the UI; no database action is needed.

v1.5.0 没有新增表或字段；它保存的 Variant 是普通的 Vault 版本，v1.4.1 可直接读取。回退到 v1.4.1 后界面不再提供复制 Variant 和向已有 Item 导入；不需要任何数据库操作。
