# Reload Viper with immutable snapshots

The Viper Handler exposes Load, Current, explicit Reload, one explicitly started Watch loop stopped by its Context, and a Change Callback around an atomically held Snapshot. Reload and Watch use the composite ETag, and every changed response constructs a new validated Viper before atomically installing it rather than mutating one already in use. Watch defaults to a jittered 30-second interval, rejects intervals below 5 seconds, and backs repeated failures off to at most 5 minutes before resetting after success. Initial load, unchanged checks, and failed reloads do not invoke the callback; a changed Snapshot is installed before its serialized callback runs outside the fetch/install lock, and callback failure does not roll it back. An unchanged Reload may complete while a callback is running; an overlapping changed Reload returns `ErrReloadRunning` without installing another Snapshot, so callbacks cannot overlap. Previous and current Snapshots are read-only to callers, and Watch may advance directly to the latest available version rather than replaying intermediate Revisions, while fetch or parse failure retains the Last-known-good.

The `configra-go` V1 API names these operations `Load`, `Current`, `Reload`, and `Watch`. `Snapshot` exposes immutable version metadata plus Viper `Unmarshal`, without exposing a mutable `*viper.Viper`. `Reload` returns whether it installed a change and reports a synchronous callback failure; the long-running `Watch` reports fetch, parse, and callback failures through `OnError` while continuing with the Last-known-good. The shared Client also exposes exact `ReadResolvedConfig` and `ReadFile` methods and preserves the standard `tls.Config.GetClientCertificate` callback for runtime certificate rotation.
