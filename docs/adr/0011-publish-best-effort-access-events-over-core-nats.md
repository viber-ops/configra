# Publish best-effort Access Events over Core NATS

API Server publishes Access Events without delaying responses through the platform's existing Core NATS when it returns resource content, and Management Server consumes them into ClickHouse for detailed records and statistics. Management Server also publishes them when a human receives Config content, Vault Text, a revealed Secret, a File, or a Resolved Preview; list and metadata-only views do not qualify. Events identify the machine or human principal, authentication context, resource, and version without values. Conditional Config Watch checks that return `304 Not Modified` increment operational metrics but do not create detailed Access Events. Delivery loss, including while the single Management Server replica is unavailable, is accepted and exposed as a dropped-event metric; persisted Access Events default to 90-day retention, while Mutation Audit Events reach ClickHouse through a durable MySQL Transactional Outbox. Dashboards report Observed Requests rather than total or audited requests. This favors read availability and reuses existing infrastructure instead of presenting access history as a complete compliance audit.

The V1 Core NATS subject is `configra.v1.access` and every strict, value-free envelope carries `schema_version: 1`. API Server uses an 8 MiB bounded reconnect buffer. Management Server uses the `configra-management-v1` queue group with an 8192-message bounded channel and writes batches of at most 500 events or every 250 ms; the queue prevents a brief deployment overlap from duplicating every observed read. Exhausted buffers, malformed envelopes, and failed ClickHouse Access batches may be dropped with metadata-only operational warnings; none may block a content response.
