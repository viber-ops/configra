## Revision history

Config and Vault revision history now use exclusive `before` cursors, 50 items by
default and a hard maximum of 100. The storage methods enforce the limit even
outside HTTP. Invalid/duplicate/unknown query parameters are rejected before
storage. The UI pages history, comparison and transfer columns without collecting
all revisions; old selections remain explicit. Existing generated UI bundles
and their license/SBOM metadata were rebuilt together. Usage instructions and the
Management query contract are in [the UI guide](../ui.md#revision-history--历史版本).

The real HTTPS test creates 1,005 Config and Vault revisions each, starts paging,
then writes revision 1,006. It verifies complete descending continuation without
duplicates, independent Environment/Namespace histories, archived history,
empty/end pages, missing identities and absence of source/secret/file values in
metadata. The first run passed with a largest response of 16,825 bytes and a
slowest page of 11.55 ms. Identity is supplied at the external authentication
adapter; this is not the separate full OIDC deployment gate.
After the SQL ordering correction, the same race-enabled HTTPS test also passed
on minimum Go 1.25.13: 51.06 seconds for the test, 16,824 bytes for the largest
history response and 6.87 ms for the slowest page.

The initial SQL limit was **not sufficient**: MySQL 8.0.22 performed 1,009 handler
reads for a one-item Config history page. `EXPLAIN ANALYZE` showed 1,005 matching
rows read and sorted before the two-row limit (one item plus lookahead). Making
the full primary-key ordering explicit removed that scan without adding an index.
The regression records per-connection
[MySQL handler counters](https://dev.mysql.com/doc/refman/8.0/en/server-status-variables.html#statvar_Handler_read_key),
not host-dependent latency, around the real storage methods. With 1,005 revisions,
the result was the same at the newest page, `before=500`, and `before=101`:

| Page limit | Config handler reads | Vault handler reads |
| --- | --- | --- |
| 1 | 5 | 3 |
| 50 | 54 | 52 |
| 100 | 104 | 102 |

The per-query ceiling includes parent lookups, lookahead, source joins and counter
sampling: `4 * (limit + 1) + 64`. It catches full-history scans without relying on
exact optimizer cost estimates. Sampling alone recorded zero handler reads.
This storage diagnostic is separate from HTTP acceptance; neither substitutes
for the production-image 1,000-QPS gate. Resource inventories and selectors are
covered by the later follow-up below; Vault usages remain open work.

## Offline Master Key rotation

The source candidate adds `rotate-master-key`, following
[ADR 0032](../adr/0032-rotate-local-master-keys-offline.md) and the
[maintenance runbook](../../deploy/backup/README.md#offline-master-key-rotation).
It verifies all encrypted records, rewraps their data keys, replaces the Sentinel
and records an Audit receipt in one InnoDB transaction. Payloads, CA signing
keys, revisions and ETags stay unchanged. No schema, dependency, online keyring,
automatic Secret update or background migration was added.

Vault, CA and notification writes now verify the Sentinel while holding a lock
before their other mutation locks. Rotation takes the exclusive lock; readiness
also verifies the Sentinel. The locking behavior uses MySQL 8.0.22
[locking reads](https://docs.oracle.com/cd/E17952_01/mysql-8.0-en/innodb-locking-reads.html).
These guards cover current code, **not** older binaries or arbitrary SQL writers.
The operator must stop all replicas and automatic restarts before rotation.

## Native reconciliation ordering and request bounds

remain. All four Secret/ConfigMap × missing/existing cases fail against the old

no-op shortcut.
