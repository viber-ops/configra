## Retained first hosted capacity failure

[Acceptance run 38771083160](https://github.com/viber-ops/configra/actions/runs/38771083160)
on `362ca43` passed real integration and the complete three-node Kubernetes,
backup, offline-key rotation, restored-CA and post-rotation delivery checks.
The capacity step failed during its 15-second warmup: 11,833 requests,
788.75 requests/s, 730.78 completed requests/s; 11,827 HTTP 200 responses and six
client timeouts. Warmup p95 was 2.638 seconds. The host reported four Linux/amd64
CPUs, with the API constrained to two CPUs / 512 MiB. The measured ten-minute
stage did not run, so this is not passing capacity evidence.

The old sampler began after warmup, leaving no CPU/memory/MySQL samples for this
failure. Warmup is now sampled too, using the existing bounded metadata collector
and secret-filtered report. Request-rate, timeout, zero-error, memory and leakage
thresholds are unchanged. The cause is not assigned to the host or runtime without
further evidence. Raw results and API logs remain private; CI prints only bounded
metadata. The normal CI run on the same candidate passed all checks.


## Second capacity attempt and bounded SQL reuse

[Capacity run 38776404451](https://github.com/viber-ops/configra/actions/runs/38776404451)
on `3b7944e` passed warmup and ran the full ten-minute measurement, but failed the
unchanged zero-error gate: 596,544 requests, 994.21 sent/s, 992.71 completed/s,
596,523 HTTP 200 responses and 21 client timeouts. Measured p95 was 2.044 seconds.
Warmup showed about 109–111% API CPU with 18–21 MySQL connections and 3–5 running
threads. This is retained as a failure, not converted into passing evidence.

A real-MySQL regression then demonstrated avoidable authentication overhead:
40 token/certificate reads caused 40 preparations. Reusing only the two fixed
SQL statement plans reduces this to at most two preparations on one connection.
The SQL and parameter binding are unchanged. Grant removal, token revocation and
expiry, certificate revocation, initial cancellation, new pooled connections and
concurrent reads remain effective in real MySQL race tests. No authorization
result or credential is cached; failed prepares are retried and Store.Close
releases the bounded statements. Read-only review found no important issue.

A matched Go 1.26.9 local ARM64 image smoke test (API 2 CPUs/512 MiB, same host
and 15-second measurement) completed 15,000 requests with zero errors before and
after this change. Prepared statements per second fell from about 7,434 to 5,008;
p95 went from 14.52 to 10.91 ms and p99 from 50.58 to 23.48 ms. These short results
do not replace the ten-minute gate or establish the cause of every hosted timeout.
The candidate is revalidated with the original complete gates before publication.

Local image builds used Google’s Docker Hub mirror for the same pinned Node/Go
manifest digests because direct Docker Hub resolution timed out. Source stages,
contents, CPU/memory limits and image verification were unchanged. Actual image
composition and non-root/read-only checks passed. Both warmup and measured sample
metadata are now reported even when a throughput check fails; cumulative MySQL
connection and prepare counters help diagnose churn without exposing SQL input.
