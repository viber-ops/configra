# MySQL 8.0.22 and 8.4 compatibility for Configra

Research date: 2026-09-11. Scope: Configra's checked-in Go driver, SQL, bootstrap, tests, and logical backup tools, compared with official MySQL/Oracle documentation and first-party source. MySQL **8.0.22 remains a required application target**. This report does not authorize a database upgrade.

## Finding

The inspected application code has no identified SQL or Go-driver blocker to adding MySQL 8.4 support while retaining 8.0.22. This is a source-based assessment, not a completed compatibility certification. The existing test configuration and backup/restore tools explicitly target 8.0.22; they do not currently establish an 8.4 recovery contract.

Three questions require separate answers:

| Question | Assessment |
| --- | --- |
| Can the same Configra application run against independently provisioned 8.0.22 and 8.4 databases? | Plausible from the inspected SQL and driver; run the existing behavioral tests against both. |
| Can an existing 8.0.22 instance be upgraded to 8.4? | An installation-specific migration requiring MySQL's upgrade checks, configuration/authentication review, and a recovery plan. Application compatibility does not establish this. |
| Can Configra's current backup tools recover an 8.4 deployment? | No: both scripts deliberately reject servers other than exactly 8.0.22, and their client checks also reject 8.4 clients. |

The last row is directly observable in [mysql-backup.sh](../../deploy/backup/mysql-backup.sh) and [mysql-restore.sh](../../deploy/backup/mysql-restore.sh).

## Authentication and connection differences

`caching_sha2_password` is already the default in MySQL 8.0, including the 8.0.22 baseline; it is also the default in 8.4. The relevant change is that **8.4 disables the server-side `mysql_native_password` plugin by default**. Existing accounts do not automatically acquire a different authentication plugin merely because the server's default changes. A legacy native-password account therefore needs explicit handling during an upgrade. [MySQL 8.0 authentication changes](https://dev.mysql.com/doc/refman/8.0/en/upgrading-from-previous-series.html#upgrade-caching-sha2-password), [8.4 native authentication](https://dev.mysql.com/doc/refman/8.4/en/native-pluggable-authentication.html)

For a new 8.4 deployment, use `caching_sha2_password` accounts. Where an operator requires a temporary legacy-account bridge, 8.4 can enable native authentication with `mysql_native_password=ON`; the old `default_authentication_plugin=mysql_native_password` setting is removed in 8.4 and is not a substitute. These are server-version-specific settings, not options to add indiscriminately to an 8.0.22 configuration. [8.4 native authentication](https://dev.mysql.com/doc/refman/8.4/en/native-pluggable-authentication.html), [removed server variables](https://dev.mysql.com/doc/refman/8.4/en/added-deprecated-removed.html)

The pinned Go driver's [authentication source](https://github.com/go-sql-driver/mysql/blob/v1.10.0/auth.go) implements both plugins, including SHA-2 full authentication over TLS/Unix sockets and RSA password exchange over TCP. Thus an error from a native-password account on default 8.4 is not, by itself, evidence of a Go-driver incompatibility.

Validate the actual production DSN, certificates, account plugin, and client defaults. Full SHA-2 authentication requires secure transport or RSA password exchange; cached authentication can hide a broken full-authentication setup until a restart or cache clear. MySQL CLI clients have explicit public-key options, while this Go driver can request a key in its authentication implementation. A successful Go connection therefore does not establish that `mysql`/`mysqldump` use the same transport/authentication configuration. [SHA-2 connection and cache behavior](https://dev.mysql.com/doc/refman/8.4/en/caching-sha2-pluggable-authentication.html), [driver authentication source](https://github.com/go-sql-driver/mysql/blob/v1.10.0/auth.go)

## Existing-instance upgrades: exact scope of the prerequisites

Oracle's general upgrade table permits the 8.0 bugfix-series to 8.4 LTS path using in-place upgrade, logical dump/load, or replication. It does not turn application support for 8.4 into permission to replace an 8.0.22 instance. [General upgrade paths](https://dev.mysql.com/doc/refman/8.4/en/upgrade-paths.html)

**Do not present “8.0.35 is universally required before 8.4” as a verified server rule.** The official Windows **MySQL Configurator** page specifically lists `8.0.35+ → 8.4` among that tool's supported in-place scenarios. The general server upgrade table does not state this patch minimum. [Configurator's supported paths](https://dev.mysql.com/doc/refman/8.4/en/mysql-configurator-workflow-server.html)

As corroborating implementation evidence, the official 8.4.0 bootstrap source includes `DD_VERSION_80022` in its supported data-dictionary versions. Its `80035` threshold controls reading newer release-maturity/upgrade metadata; it is not a blanket rejection of an older 8.x server upgrading to 8.4. This supports the tool-specific reading above, but is not a runtime validation of an arbitrary 8.0.22 data directory or the newest 8.4 artifact. [Tagged bootstrap context](https://github.com/mysql/mysql-server/blob/mysql-8.4.0/sql/dd/impl/bootstrap/bootstrap_ctx.h#L78), [tagged version checks](https://github.com/mysql/mysql-server/blob/mysql-8.4.0/sql/dd/impl/bootstrap/bootstrapper.cc#L1180)

For an operator who separately elects to migrate an instance:

1. Rehearse with a recoverable copy and the exact chosen distribution/version. Updating through the final 8.0.46 patch before 8.4 follows MySQL's recommendation to update the existing series first; it is an operational migration choice, not a new Configra application minimum. [8.0 upgrade paths](https://dev.mysql.com/doc/refman/8.0/en/upgrade-paths.html)
2. Run a compatible MySQL Shell upgrade checker with an explicit `targetVersion`, supplying the server option file where applicable. Review both automated findings and required manual checks. The checker accepts 8.x GA sources, including the 8.0 series, and requires `SELECT`/`PROCESS` privileges. It does not exercise application behavior. [Upgrade checker](https://dev.mysql.com/doc/mysql-shell/26.7/en/mysql-shell-utilities-upgrade.html)
3. Resolve installation-specific problems: removed options/SQL modes, incompatible object definitions or identifiers, problematic partitioning, authentication accounts, and any incomplete previous upgrade. Review the full prerequisites, not just Configra's schema. [Upgrade prerequisites](https://dev.mysql.com/doc/refman/8.4/en/upgrade-prerequisites.html)
4. For in-place replacement, perform a proper clean shutdown. The documented procedure requires changing `innodb_fast_shutdown=2` to `1` or `0`; after an unexpected shutdown, the prerequisites call for restarting the old server and shutting it down with `0`. The new server upgrades the existing dictionary/system metadata. [In-place procedure](https://dev.mysql.com/doc/refman/8.4/en/upgrade-binary-package.html), [shutdown prerequisite](https://dev.mysql.com/doc/refman/8.4/en/upgrade-prerequisites.html)
5. For logical migration, load reviewed application SQL into a fresh 8.4 data directory. Oracle explicitly warns that exported SQL may require changes. Loading Configra's application-schema dump does not migrate server configuration, users, or privileges, which must be provisioned separately. Direct 8.0.22 application-schema export to fresh 8.4 is a reasonable rehearsal candidate under the documented series path; it was not executed here. [Logical upgrade procedure](https://dev.mysql.com/doc/refman/8.4/en/upgrade-binary-package.html), [Configra dump scope](../../deploy/backup/mysql-backup.sh)

The 8.4 default restriction on *creating* nonstandard foreign keys also illustrates why fresh-schema testing and in-place testing differ: Oracle allows upgrades of existing 8.0 foreign keys that reference nonunique/partial keys, with warnings, even though new definitions are rejected by default. Configra's inspected schema does not use this extension. [8.4.0 foreign-key upgrade behavior](https://dev.mysql.com/doc/relnotes/mysql/8.4/en/news-8-4-0.html)

Do not restart 8.0.22 on a data directory already upgraded by 8.4. Oracle's cross-series downgrade table lists logical dump/load or replication only, and only for rollback where new server functionality has not been applied to the data. It does not certify an arbitrary 8.4 dump for 8.0.22. Keep a separately usable pre-upgrade recovery point and rehearse any required reverse logical path. [Downgrade paths](https://dev.mysql.com/doc/refman/8.4/en/downgrading.html)

## Backup/client compatibility needs its own validation

The current scripts check exact 8.0.22 client and server versions. Backup dumps one selected database with `--single-transaction --quick --hex-blob --set-gtid-purged=OFF --no-tablespaces --column-statistics=0 --skip-comments`. Restore verifies the checksum and creates a new database. Its same-version round trip and Crypto Sentinel checks are covered by an integration test that launches `mysql:8.0.22` clients. [Backup script](../../deploy/backup/mysql-backup.sh), [restore script](../../deploy/backup/mysql-restore.sh), [backup integration test](../../internal/storage/mysqlstore/backup_restore_integration_test.go)

The used dump options remain documented in 8.4. With InnoDB, `--single-transaction` gives a consistent snapshot but concurrent schema DDL can invalidate it. `--no-tablespaces` avoids the dump's `PROCESS` requirement; `--set-gtid-purged=OFF` avoids emitting GTID-purged state. Treat grants and dump/restore execution as explicit test inputs. [8.4 mysqldump](https://dev.mysql.com/doc/refman/8.4/en/mysqldump.html)

Newer dumps can also contain newer replication/event terminology. The 8.4 dumper offers `--output-as-version=BEFORE_8_0_23` for older targets such as 8.0.22; its effect is limited to specified replication/event output, not universal SQL compatibility. Configra's current backup command does not request those outputs, so this is relevant to expanded recovery workflows rather than a demonstrated current failure. [8.4 dump output-version option](https://dev.mysql.com/doc/refman/8.4/en/mysqldump.html#option_mysqldump_output-as-version)

For future 8.4 recovery support, test explicitly selected server/client pairs and record actual server version, client version, image digest/package identity, and relevant defaults. Do not merely remove the exact-version checks and assume all combinations work. Preserve the current 8.0.22 pair and its recovery behavior.

## Missing evidence and actionable recommendation

No databases or containers were started, no application integration suite was run, and no live installation was inspected for this research. There is no result here proving 8.4 initialization, migrations, concurrent mutation semantics, latency, or restore integrity. The Compose test service remains pinned to `mysql:8.0.22`; multiple storage and E2E helpers explicitly require that version, and some tests skip when DSNs are absent. A generic green `go test` result would therefore not establish dual-server coverage. [Compose](../../deploy/compose.test.yaml), [authority helper](../../internal/storage/mysqlstore/authority_integration_test.go), [machine helper](../../internal/storage/mysqlstore/machine_integration_test.go), [SDK E2E helper](../../e2e/sdk_integration_test.go)

Keep **8.0.22 as the required compatibility floor** and preserve its test/recovery lane. Add an independent 8.4 lane with a verified current artifact and run the same bootstrap/migration, Config/Vault, session/credential, concurrency/outbox, and backup/restore cases, including correct/wrong Master Key and corrupt-artifact checks. Validate SHA-2 full authentication and any intentionally supported legacy-account configuration. Only then advertise the tested 8.4 deployment/recovery combination. No driver replacement or broad SQL rewrite is indicated by the current evidence; the two deprecated upserts can be modernized independently without raising the 8.0.22 floor.
